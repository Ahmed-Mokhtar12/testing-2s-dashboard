# Security & Code Audit — testing-2s-dashboard.digitlab.ai (2026-09-01)

**Status: COMPLETE. Nothing in the repo, on the host, or on the Supabase platform was changed. The only live calls were read-only catalogue queries and two header-less GETs used to prove a public endpoint is public.**

## Executive summary — the ten things that matter most

**Production is exposed to every database/edge/cron finding below**: `2s-dashboard.digitlab.ai` and this testing site are two frontends on **one shared Supabase project** (`yczcebfaqerlwfalrbjn`, verified in both checkouts). Only the WhatsApp-UI findings (§3) are testing-only.

1. **`whatsapp-web-chat` is world-callable with no key at all** (E1/CR1, Critical) — anyone can insert fake guest messages under any real guest number, plant a foreign attachment URL that every operator's browser auto-loads, trigger the paid AI pipeline, pin conversations in human mode, and extract a guest's pre-release chat history through the AI's reply. `config.toml` claims it "carries its own in-body auth"; it does not. Verified on the deployed source and by a header-less GET to its sibling.
2. **`execute-n8n-action` is an open, HMAC-signed relay to n8n's send-email/SMS/WhatsApp webhook** (E2, High→Critical if the workflow is live).
3. **WhatsApp auto-release has been dead since 2026-04-23** — 188,275 consecutive pg_cron failures (`permission denied for function http_post`, wrong role) and nothing alerted (L1). Five conversations are stuck in human mode, four for >1 day. The guest-email purge job has likewise failed 840× since a table rename; 699 threads retained instead of 48 h (L2).
4. **Three tables have RLS off and full anon read/write/delete** — `qms_request_log` (guest name, room, reservation, request text), `integrity_check_history`, `n8n_chat_histories_backup_serafix_20260824` (L3). Created by platform-only migrations; the RLS sentinel that would have caught them is not scheduled.
5. **The live `whatsapp-send-message` has no staff gate and no attachment allowlist** (E3) — the git fix exists but is undeployed; the role-less `sera@` account (a real session) can message any number with any link and take over any conversation.
6. **Every Sera turn is written to a staff-wide table with no `user_id` and injected into every other user's prompt** (E4) — cross-user and cross-role leak of whatever anyone asked or was told.
7. **Sera's chat panel infinite-loops on the first message of a new session** (A1, reproduced) and **silently stops persisting history past ~125 KB** (A2, measured).
8. **Dashboard dates are wrong for any browser not at UTC+4** — a double timezone shift in presets (A4) plus browser-local bucketing in trends (A5); invisible to Playwright because the server is at +4.
9. **Root everywhere + a management token in root's bash history** (I1, I2) — nginx, PM2 and `serve` run as root; the `sbp_` token that can deploy arbitrary edge code sits in `.bash_history` 5× and in `curl` argv on every deploy.
10. **Any staff JWT can rewrite every column of any guest's chat row through PostgREST** (D3), and a guest can crash the entire WhatsApp inbox for every operator with one long formatted message (CR5).

**What is clean, stated plainly:** there is **no SQL/PostgREST/OData injection** anywhere in frontend or edge code; **no XSS sink**; **no secret in git history, bundles, docs or logs**; no privilege-escalation path through `user_roles`; storage buckets are private and staff-gated; the deploy scripts are sound; and the two platform-only ingest functions are exemplary. The security posture is not "no controls" — it is a small number of unauthenticated side doors next to a mostly well-locked front door, plus monitoring that never fires.

## Context

Ahmed asked for a full, read-only security review (SQL injection and any other bugs) of the whole site, to be followed by a separate planning step for fixes. Method: `security-coverage` layer model (S0–S11), the repo's own conventions (CLAUDE.md, docs/testing-lessons.md, docs/backlog.md), live read-only inspection of the Supabase project (catalogue, policies, grants, cron, advisors), and seven parallel read-only audit agents over the code plus the eight-angle `code-review` pass over the recent WhatsApp commits. Every finding below is either verified against code/catalogue or marked with its confidence.

Severity scale: **Critical** = exploitable now by an unauthenticated party or a live production outage; **High** = exploitable by any authenticated user / wrong data or data loss in production; **Medium** = realistic edge condition or defence-in-depth gap; **Low/Info** = hygiene.
